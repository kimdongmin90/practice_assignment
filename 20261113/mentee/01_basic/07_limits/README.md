## 2. 사실성·형식·근거 검증의 개념적 분리 설명

LLM 응답의 신뢰성을 확보하기 위해서는 **형식(Format), 근거(Evidence), 사실성(Factual)** 검증을 하나의 단일 검사가 아닌 **서로 독립된 별개의 검증 계층**으로 나누어 수행해야 합니다.

* **형식 검증 (`format`) — 구조적 무결성 확인**
  * **목적:** AI의 출력물이 시스템이 파싱할 수 있는 약속된 스키마(JSON 키 존재 여부, 데이터 타입 등)를 지켰는지 검사합니다.
  * **독립성:** 답변 내용이 아무리 정확하더라도(`F02` 사례), 데이터 구조가 깨져 있으면 다음 프로그램 단계에서 `KeyError` 등의 런타임 장애를 유발하므로 가장 먼저 걸러내야 합니다.
* **근거 검증 (`evidence`) — 인용 및 출처 존재 여부 확인**
  * **목적:** AI가 답변을 생성할 때 참조한 지식 베이스 문서 ID(`sources`)가 실제로 명시되어 있는지 확인합니다.
  * **독립성:** 형식이 완벽하더라도 근거가 비어 있다면(`F03` 사례), 사용자가 해당 답변의 진위를 추적하거나 검증할 수 없으므로 환각(Hallucination) 위험이 발생합니다.
* **사실성 검증 (`factual_mismatch`) — 원본 데이터와의 내용 일치성 확인**
  * **목적:** 형식과 출처 표기를 모두 갖추었더라도, 실제 인용된 원본 문서(`source`)의 의미와 AI가 생성한 문장(`answer`)이 모순되지 않는지 대조합니다.
  * **독립성:** 출처를 달아놓고도 내용을 왜곡해서 지어내는 경우(`F01` 사례)를 잡아내기 위한 최상위 의미론적 검증 단계입니다.

## 3. 검증 결과 요약 및 향후 후속 업무 보완사항

### 생성된 산출물 요약
* **`outputs/review.json`**: 분류 결과(`classification`), 오류 정의(`definitions`), 면책 조항(`disclaimer`)이 포함된 구조화 데이터 저장 완료.
* **`outputs/review.md`**: 사례별 분류 결과 및 플랫폼 아키텍처 연결 요약(FastAPI·PostgreSQL·RAG·Agent) 문서 생성 완료.

### 향후 후속 업무 진행을 위한 보완사항
현재 스크립트에서 빈 값으로 남겨둔 거버넌스 항목들을 고도화하여 다음과 같이 보완할 계획입니다.

1. **완화 전략(`mitigation`) 구체화 및 자동화**
   * `format` 오류 방지를 위해 FastAPI와 연동된 **Pydantic 출력 파서(Structured Outputs)**를 강제합니다.
   * `evidence` 누락 시 답변 출력을 차단하고 RAG 검색 재시도(Retry) 또는 "근거 부족" 안내 문구를 반환하도록 예외 처리를 추가합니다.
2. **추가 검증 로직(`additional_checks`) 도입**
   * 현재는 문자열 단순 일치(`answer != source`)로 비교하고 있으나, 향후 임베딩 유사도 검사나 LLM-as-a-Judge 기반의 **의미론적 사실성 검증**으로 확장합니다.
   * 인용된 출처 ID(`K01` 등)가 실제 PostgreSQL 원본 테이블에 존재하는 유효한 키인지 교차 검증합니다.
3. **에이전트 통제(`agent_case`) 및 신뢰 규칙(`trust_rules`) 수립**
   * 검증을 통과하지 못한 응답이 외부 도구(파일 수정, DB 쓰기 등) 실행으로 이어지지 않도록 **사용자 승인(Human-in-the-loop)** 안전장치를 적용합니다.
