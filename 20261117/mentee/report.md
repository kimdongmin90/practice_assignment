# 11/17 수업 내용 정리: LLM API 클라이언트 전체 흐름과 설계 원칙

## 📌 전체 흐름 (AI Agent가 재사용할 모델 호출·검증·기록 파이프라인)

```text
[Context 구성] ➔ [Prompt 조립] ➔ [LLM Client] ➔ [완료, 출력 검사] ➔ [재시도, 중단] ➔ [측정, 평가]
```

* **핵심 역할:** 질문, 모델 설정, API 인증 정보를 입력받아 외부 모델에 요청을 보낼 연결을 준비하고, 응답 객체 또는 연결 오류를 반환합니다.

---

## 1. 모델을 호출하는 한 번의 작업
* **LLM Client의 역할:** 인증, 모델 지정, 전송을 담당하며 API 수신, Streaming, 오류 정책, 비용/시간 기록, 캐시와 모델 선택을 유기적으로 연결합니다.
* **확장 시점:** 검색(RAG)과 도구(Tool) 실행은 기본 호출/검증 파이프라인이 완성된 이후에 추가됩니다.
* **보안 및 권한 원칙:** 모델이 유효한 JSON 응답을 반환했다고 해서 **도구를 실행해도 된다는 권한(승인)을 의미하지는 않습니다.**

---

## 2. 입력의 역할과 출력의 검사
* **프롬프트 구조:** `instructions`(시스템 지시사항) + `input`(사용자 질문/데이터) = `prompt`
* **구조 제약의 한계:** Structured Outputs는 출력의 **형식(구조)만 제약**할 뿐입니다.
  * **구조 통과 ≠ 근거 적합 ≠ 사람 승인** (각 단계의 검증은 별개입니다.)
* **필수 필드 설계:** 완료 출력 검사 시 기본값이 없는 4가지 핵심 필드는 모두 필수적으로 포함되어야 합니다. *(현업 및 후속 LLM 입력 구조에서도 널리 활용)*
* **근거 및 중복 검증:**
  * 출처(Source)의 실제 존재 여부는 DB 기반의 자동 스캐닝(auto-scanning)으로 검증할 수 있습니다.
  * `set()` 함수는 출처 ID 등의 중복 처리를 위해 사용합니다.

---

## 3. 먼저 보여도, 아직 확정할 수는 없습니다 (Streaming 처리)

### ① 응답 수신 방식 비교
* **Non-streaming:** API 응답이 완전히 준비될 때까지 기다린 뒤 전체 결과를 한 번에 받습니다.
* **Streaming:** 전체 응답이 끝날 때까지 기다리지 않고, 생성 중 도착하는 텍스트 조각(Chunk)을 먼저 받는 방식입니다. *(LLM·VLM 엔지니어에게 매우 중요한 처리 기법)*
  * 연결을 유지하며 이벤트를 순서대로 수신합니다.
  * **진행 순서:** `요청` ➔ `부분 수신` ➔ `완료` ➔ `검증`
  * 앞부분을 먼저 사용자에게 보여줄 수 있지만, **마지막에는 반드시 전체 결과를 확정하고 검증**해야 합니다.

### ② 완료 상태(`response.completed`)에 따른 처리
1. **완료 응답을 받은 경우:** 최종 원문과 토큰 사용량(`usage`)을 확인하고 기존 검증기로 넘깁니다. *(단, 근거 검토는 여전히 남아 있습니다.)*
2. **중단 / 거절 / 불완전인 경우:** 실패 이유를 기록하고, 부분적으로 생성된 JSON을 정상 답변으로 쓰거나 **성공 캐시에 저장하지 않습니다.**

### ③ 스트리밍 측정 시 주의점
* **조각(Chunk) 10개 ≠ 출력 10 Token** (전송 단위와 토큰 단위는 다릅니다.)
* **첫 텍스트가 빠름 ≠ 총 완료 시간이 짧음**
* **TTFT (Time To First Token):** 첫 토큰이 도착하기까지 걸린 시간입니다. 단, 클라이언트에서 측정한 TTFT가 API 서버 내부의 정확한 첫 토큰 생성 시각과 완전히 같다고 단정할 수는 없습니다.

## 4. 실패 원인에 따라 다음 행동이 다릅니다
실패 발생 시에는 **실패 원인, 현재 상태, 남은 예산(시간/횟수/비용)**을 먼저 확인한 뒤 유형별로 다르게 대응합니다.

### ① 실패 유형별 대응 전략
1. **설정 · 권한 · 한도 오류:** 잘못된 요청이나 할당량(Quota) 문제는 반복 전송으로 해결되지 않습니다. 설정을 확인하고 **즉시 중단**합니다.
2. **일시적 제한 (Rate Limit 등):** 세부 원인을 확인한 뒤, 서버가 안내한 `Retry-After`의 **최소 대기 시간**과 남은 시간·횟수 예산을 지킨 경우에만 재전송합니다. *(서버의 최소 대기를 임의로 줄여서 보내지 않습니다.)*
3. **출력 · 수신 문제:** `JSON`이나 `Schema` 같은 **형식 오류만 딱 1번 수정(Repair)**하여 재시도합니다.
   * 거절(Refusal), 출처 오류, 정보 부족, Timeout 등은 같은 형식 수정 루프로 보내지 않습니다.

### ② 주요 재시도 개념 구분
* **Exponential Backoff:** 실패가 반복될수록 재시도 대기 시간을 지수적으로 늘리는 방식입니다.
* **Jitter:** 여러 요청이 동시에 재시도되어 서버에 몰리는 현상을 막기 위해 재시도 시점을 분산시키는 작은 무작위 지연 시간입니다.
* **통신 재시도(Transport retry) vs 형식 수정(Format repair):** 통신 장애는 단순 재시도(Retry)로 처리하지만, JSON·Schema 오류는 검증 및 프롬프트 수정을 거쳐 처리합니다.

## 5. 포함 관계와 측정 구간을 맞춥니다
* **상태 값의 엄격한 구분:**
  * `None`: 미관측 (측정되지 않음)
  * `0`: 관측된 0 (실제 측정값이 0임)
  * `not_run`: 미실행 (해당 단계가 실행되지 않음)
* **비용 기록 원칙:** 실제 청구된 **알려진 비용의 소계**와 응답이 끊기는 등으로 확인되지 않은 **미확인 전송**을 구분하여 따로 기록합니다.

---

## 6. 재사용과 모델 선택은 서로 다른 정책입니다

### ① 캐시(Cache)의 3가지 분류

| 구분 | 재사용 대상 | 특징 및 경계 |
| :--- | :--- | :--- |
| **Response Cache** | 승인된 최종 답변 | 유효한 Hit 발생 시 **새 API 전송 자체를 생략**할 수 있습니다. |
| **Prompt Caching** | 같은 입력 앞부분의 계산 | 새 API 요청과 새로운 출력 생성은 계속됩니다. 입력 처리의 KV 상태를 재사용하지만, 앱의 최종 답변 캐시와는 목적과 경계가 다릅니다. |
| **KV Cache** | 모델 내부의 Key·Value 상태 | 추론 연산 효율화를 위한 모델 레벨 캐시이며, 최종 답변을 보관하는 앱 저장소가 아닙니다. |

### ② 캐싱 위치 및 모델 라우팅 전략
* **최적의 캐싱 위치:** 빠르게 캐싱을 적용하려면 **Prompt 조립 단계**나 **LLM Client 단계**에서 처리하는 것이 좋습니다. *(재시도·중단 단계나 측정·평가 단계에서는 분기 처리가 많아져 복잡도가 급격히 올라갑니다.)*
* **Model Routing:** 실제 API를 호출하기 전에 조건에 맞는 모델을 선택하는 전략입니다. *(교안의 `fast`, `quality`는 설정된 모드 이름일 뿐, 절대적인 성능 우열을 보장하는 것은 아닙니다.)*
