## 1. Document Collection (문서 수집)
* **기본 처리 흐름:** 원문 파일 ➔ Chunk ➔ `E5` + `pgvector`
* **Parsing vs Chunking 개념 비교:**

| 구분 | 역할 및 개념 | 작업 단계 | 범위 |
| :--- | :--- | :--- | :--- |
| **Parsing** | 외부에서 자료를 읽어오고 구조를 해석하는 작업 | 선처리 작업 | 더 큰 개념 |
| **Chunking** | 문서의 의미를 보고 검색 가능한 단위별로 나누는 작업 | 후처리 작업 | 더 작은 개념 |

---

## 2. Document Parsing (문서 파싱) ⭐중요
* **스키마 통일 원칙:** 원본 문서 형식(`.txt`, `.pdf`, `.md` 등)이 다르더라도 **DB에 저장되는 속성(필드 구조)은 모두 동일**해야 합니다.
* **결측치 표현 규칙:** `.txt` 문서처럼 페이지 개념이 없는 경우, **Python에서는 `None`**, **DB에서는 `NULL`**로 표기합니다.

---

## 3. Text Cleaning (텍스트 정제)
* **Cleaning(정제):** 원본 텍스트에서 불필요한 노이즈를 걷어내고 실제 필요한 내용만 뽑아내는 작업입니다.
* **Unicode Normalization (유니코드 정규화):** 겉으로 같아 보이는 글자가 서로 다른 코드포인트 순서로 표현될 때, 비교·검색하기 쉽게 만드는 표준 변환입니다.
  * **NFC:** 유니코드에서 **정준적**(표준 규칙상 겉모습도 같고, 뜻과 역할까지 100% 똑같은 본질적인 기준)으로 동등한 표현을 분해한 뒤 가능한 경우 다시 조합하는 정규화 형식입니다. *(주로 수식 등에 사용, 약한 정규화)*
  * **NFKC:** 정준 등가뿐 아니라 **호환 관계의 문자**까지 분해하고 다시 조합하는 형식입니다. *(주로 일반 본문 내용에 사용, 강한 정규화)*
  * *※ 주로 사용하는 경우는 위와 같지만, 데이터 특성과 상황에 따라 다르게 적용할 수 있습니다.*
* **검증 방법:** Cleaning 규칙 적용 전/후(`Before` / `After`) 비교 시 **`manifest`**나 **`json`** 결과 파일을 확인하며 판단합니다.

## 4. Chunking Strategies (청킹 전략)
* **Chunk:** `ParsedUnit`의 `clean_text`에서 만든 **검색(출처)·Embedding의 기본 단위**입니다. *(보통 `.` 마침표·문장 단위를 기준으로 청크를 나눕니다.)*
* **Chunk Size:** 사용하는 임베딩 모델이나 LLM의 **토큰(Token) 한도**에 따라 결정합니다.
* **Overlap 비율:** 문맥 단절을 막기 위해 앞뒤 청크를 겹치는 비율로, 상황에 따라 정하지만 **보통 10 ~ 20%** 수준으로 설정합니다.

## 5. Chunk Validation (청크 검증 및 검색 평가) ⭐중요
* **Retrieval Metrics (검색 평가 지표):** RAG나 검색 엔진에서 사용자의 질문에 대해 검색기(`Retriever`)가 정답 문서를 얼마나 빠짐없이, 정확하게, 위쪽 순위에 잘 찾아왔는지 점수로 측정하는 기준입니다.
  * *중요성:* LLM에게 아무리 좋은 프롬프트를 주어도 검색기가 엉뚱한 문서를 가져오면 환각(Hallucination)이 발생하므로, 검색 성능을 객관적으로 평가하는 Retrieval Metrics는 RAG 파이프라인 개선의 핵심입니다.

### ① 순서를 고려하지 않는 기본 지표 (Set-based Metrics)
검색된 상위 K개(`Top-K`) 결과 안에 정답 문서가 **‘포함되어 있는지’**만 따지고, 1등으로 나왔는지 5등으로 나왔는지는 구분하지 않는 지표입니다.
* **Hit Rate @K (적중률):** 상위 K개 안에 정답 문서가 하나라도 포함된 비율
* **Precision @K (정밀도):** 가져온 K개 문서 중 실제 정답 문서의 비율
* **Recall @K (재현율):** DB 내 전체 정답 문서 중 상위 K개 안에 찾아낸 정답의 비율

### ② 순위(Ranking)까지 평가하는 지표 (Order-aware Metrics)
LLM은 프롬프트의 맨 앞부분에 배치된 문서에 더 집중하는 경향(*Lost in the Middle* 현상)이 있으므로, **정답 문서가 1등에 가까울수록 높은 점수**를 주는 지표입니다.
* **MRR (Mean Reciprocal Rank, 평균 역순위):** 각 질문마다 **‘첫 번째 정답 문서’**가 몇 번째 순위(`Rank`)에 등장했는지의 역수(1 / Rank)를 구해 전체 질문에 대해 평균을 낸 값입니다. *(가장 확실한 정답 하나를 최상단에 띄우는 것이 목표일 때 가장 유용)*
* **MAP @K (Mean Average Precision, 평균 정밀도):** 정답 문서가 여러 개일 때 각 정답 위치별 정밀도를 평균 낸 지표
* **NDCG @K (Normalized Discounted Cumulative Gain):** 관련도 등급과 순위별 가중치를 함께 반영해 0~1로 정규화한 지표

## 6. Metadata & Filtering (메타데이터와 필터링) ⭐중요
* **Metadata:** 본문 텍스트 외에 문서를 설명해 주는 **부가 정보(꼬리표)**로, 해당 본문이 언제, 어디서, 어떤 규칙으로 만들어졌는지 알려주는 구조화된 속성값입니다.
* **Metadata Filtering:** 벡터 유사도 검색 전후에 이 꼬리표 조건으로 검색 범위를 좁혀 정확도와 속도를 높이는 기법입니다.
  * *필요성:* 의미 기반 검색(Vector Search)만 사용하면 비슷한 단어가 들어간 다른 부서 문서나 옛날 버전의 문서까지 섞여 나오는 한계가 있으므로, 구조화된 메타데이터 필터링을 반드시 결합하여 사용합니다.

### 필터링 처리 방식 비교

| 방식 | 동작 순서 | 장점 | 단점 |
| :--- | :--- | :--- | :--- |
| **사전 필터링<br>(Pre-filtering)** | 메타데이터 조건(`WHERE`)으로 후보 추출 ➔ 추려진 후보 내에서만 벡터 유사도 계산 | 불필요한 연산이 줄어 **검색 속도가 빠르고**, 반환 개수(`Top-K`)가 항상 보장됨 | 필터 조건이 너무 좁으면 벡터 인덱스 효율이 떨어질 수 있음 |
| **사후 필터링<br>(Post-filtering)** | 전체 DB에서 벡터 유사도로 상위 N개 추출 ➔ 결과 중 메타데이터 조건에 안 맞는 항목 제거 | 기존 벡터 인덱스를 그대로 활용할 수 있어 구현이 단순함 | 조건에 안 맞는 문서가 다 걸러지면 **최종 결과가 0개**가 될 위험이 있음 |

---

## 7. pgvector Indexing Pipeline ⭐중요
* **파이프라인 범위:** 문서 수집부터 검증 · Embedding · 저장 · 공개(`Publish`)까지 이어지는 일련의 자동화 작업입니다.
* **Database Index:** 저장된 행(Row)을 처음부터 끝까지 다 뒤지지 않고 빠르게 찾도록 돕는 자료구조입니다.

---

## 8. End-to-End Integration (전체 통합 흐름)
* **데이터 변환 단계:**
  ```text
  Raw ➔ ParsedUnit ➔ CleanUnit ➔ Chunk ➔ E5 (Embedding) ➔ pgvector ➔ Retriever
  ```
* **Staging & Publish:** 새 버전 데이터를 임시로 적재(`Staging`)하고 검증한 뒤, 실제 서비스 검색 대상(`Publish`)으로 전환하여 Vector DB에서 안전하게 꺼내올 수 있도록 관리합니다.
